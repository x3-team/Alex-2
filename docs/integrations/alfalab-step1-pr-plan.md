Дата: 23.10.2026. Код не менялся. Продолжение `alfalab-lis-plan.md`; решения Виталия от 23.10 заменяют там вариант «оплата в офисе».

## 0. Сверка с PDF протокола

Второе вложение `protocol.pdf` пришло тем же текстом, что и первое: файлы совпадают побайтно, исходного PDF с таблицами у меня нет. Сверить вёрстку таблиц не с чем. По тексту видно места, где извлечение или сам протокол могли исказить поля. Их надо уточнить у лаборатории или по PDF:

| Где | Что в тексте | Что, вероятно, имелось в виду / что спросить |
|---|---|---|
| §8.2.2, §10.2.3 | заголовок `X-ExternalPassword` | скорее всего `X-External-Password` (дефис съеден переносом). Мы всё равно берём Basic |
| §11.1.2 | `DoctorProf` без типа | string. Нам не нужно (врача нет) |
| §11.1, пример 2 | `DoctorSpecialization` вместо `DoctorProf` из таблицы | расхождение в самом протоколе; нам не нужно |
| §11.1, JSON-пример | `"birthdate"` (строчная d), остальные поля в camelCase (`lastName`, `samplingDate`) | **спросить точное имя: `birthDate` или `birthdate`** |
| §10.2.3 | в таблице ответа `MessageType`, в примере `messageType` | регистр JSON-полей ответа уточнить |
| §11.17.5 | `DoctorExortCode2` (в §11.17.6 — `DoctorExportCode2`) | опечатка протокола; поле нам не нужно |
| §11.14, пример | `LisId"99999990"` без `=` | опечатка примера |
| §10.2.2 | дата `" 2 0 2 1 - 0 4 - 20T17:45:00+03:0 0"` | артефакт извлечения; формат `YYYY-MM-DDThh:mm:ss+03:00` |
| §10.1.1 | «поддерживает кодировки UTF-8 и UTF-8» | вторая, видимо, Windows-1251; для JSON неважно |
| весь документ | JSON-примеры есть только для §11.1 и общей обёртки | **попросить у лаборатории реальные JSON-ответы**: `result-import-referral`, `referral-results` (с бланком), `dictionaries`, ошибка 500 |
| §11.24 | «пример выгрузки справочников можно запросить отдельным файлом» | запросить |
| ссылки внутри | «см. 4.4.2», «10.4», «10.2» | старая нумерация разделов; на поля не влияет |

Если пришлёте PDF файлом в репозиторий или папку проекта так, чтобы он не превратился в текст, сверю таблицы по нему.

## 2. Разбивка на PR

Общее для всех PR: ветка от свежего `production`, CI на облачных раннерах, миграции только добавляют таблицы и колонки, `SITE_VERSION` поднимается в том PR, где меняется что-то видимое в сборке фронта. Существующие URL, редиректы, метатеги, sitemap и robots не меняются. Каждый PR закрыт флагом и тестами `tests/Unit`. Пушим в PR пачками, чтобы экономить минуты CI.

Объём: S — до ~10 файлов, M — 10–25, L — больше 25.

| # | PR | Зависит от | Объём | Фронт? |
|---|---|---|---|---|
| 1 | ЛИС: каркас модуля, mock-клиент, справочники, лог | — | M | нет |
| 2 | Пациенты: таблица, guard, вход по коду из письма, восстановление | — | M | бэкенд; экраны после макетов |
| 3 | ЮKassa: платежи, вебхук, чек, возвраты, тестовый режим | — | M–L | нет |
| 4 | Офисы: таблица, админка, импорт CSV, API для корзины | — | M | админка (Tailwind, без Figma) |
| 5 | Оформление: заказ → оплата → направление → статусы → PDF | 1–4 | L | нет (API и команды) |
| 6 | Экраны: корзина, выбор офиса, «спасибо», кабинет | 5 + макеты | L | да, по Figma |

PR 1–4 независимы и могут идти параллельно. PR 6 начинается только после согласования макетов.

### PR-2. Пациенты и вход (часть d)

Если нужен именно пароль, как на текущем макете, сделаем «ссылку для установки пароля» на базе механизма Breeze. Решение — вопрос 3.1.7.

### PR-3. ЮKassa (c)

- `config/payments.php`: `PAYMENTS_ENABLED=false`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_TEST_MODE`, параметры чека (СНО, НДС, признаки предмета и способа расчёта). Ключи только в `.env` на сервере.
- Клиент на `Http` (API v3): `POST /v3/payments` с `Idempotence-Key` = UUID платежа, `capture: true`, подтверждение `redirect` (платёжная страница ЮKassa), `receipt` из двух позиций с `customer.email`.
- `FakePaymentGateway` для тестов и локальной проверки без ключей.
- Вебхук `POST /api/payments/yookassa` (новый служебный URL, только POST, вне sitemap): события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Подписи у ЮKassa нет, поэтому статус всегда перепроверяем запросом `GET /v3/payments/{id}`, плюс фильтр по IP ЮKassa. Обработка идемпотентна.
- Команда `payments:sync`: досверка зависших платежей (вебхук мог не дойти).
- Возвраты: `POST /v3/refunds` с чеком возврата; из админки, полный возврат (частичный — по решению).
- Миграции: `payments`, `refunds`.
- Чеки: если расчёт до оказания услуги, это **предоплата 100 %**, и по 54-ФЗ после оказания нужен второй чек «полный расчёт». В «Чеках от ЮKassa» это делается вторым запросом `receipts` с `settlements`. Когда его отбивать (по `Activated` или `Done` из ЛИС) — решить с бухгалтером заказчика (вопрос 3.2.3).

### PR-4. Офисы (b)

- Таблица `lab_offices`: город, название, адрес, метро, часы (будни и выходные), телефон, координаты, код офиса у лаборатории, «принимает ALEX2», активность, сортировка, бейдж/акция.

- Подключение офисов к корзине на фронте — в PR-6.

### PR-5. Оформление и жизненный цикл заказа (d)

- Таблица `lab_orders`: ссылка на `orders`, на `patients`, на `payments`; `mis_id` (UUID), `nr`, `lis_id`, `office_id`, состав и цены на момент заказа, статусы (оплата и ЛИС), `lis_version`, плановые даты, ошибки, попытки.
- Сервер сам собирает корзину: ALEX2 + взятие биоматериала + выбранные доп. услуги, цены только из БД. `submission_id` защищает от двойного оформления.
- Цепочка: оформление → платёж (PR-3) → `payment.succeeded` → создание пациента (PR-2) → `lis:send` → направление в ЛИС (PR-1) → письмо пациенту с номером направления и офисом → `lis:poll` → статусы → письмо «результат готов» → PDF в кабинете через прокси §11.19.
- Неоплаченный заказ автоматически отменяется через N часов. Отмена после оплаты до активации: `query-referral-remove` + возврат.
- Ошибки: ЛИС не принял направление после оплаты → `needs_attention`, алерт на info@, в админке кнопки «повторить» и «отменить с возвратом».
- Заявка в `orders` создаётся как сейчас (письмо на info@ и аналитика не теряются). Ответы квиза в ЛИС не уходят.
- Админка: «Заказы ЛИС» (список, карточка, хронология: оплата, отправка, статусы, ошибки).
- API для экранов PR-6: оформление, статус оплаты, заказы пациента, PDF.

Корзина, выбор офиса, «спасибо» и статус оплаты, вход и восстановление, кабинет. ### 3.2 От заказчика (ООО «МФК ИНМУНОТЕХ»)

1. **ЮKassa:** договор, `shopId` и секретный ключ тестового магазина, затем боевого. Подключённые способы оплаты (карты, СБП, SberPay).
2. **Касса 54-ФЗ:** «Чеки от ЮKassa» или своя онлайн-касса (АТОЛ Онлайн, Orange Data и т.п.). ИНН, система налогообложения (`tax_system_code`), ставка НДС для каждой позиции (медуслуги по лицензии обычно без НДС — подтверждает бухгалтер), названия позиций в чеке.
3. **Предоплата и второй чек:** когда услуга считается оказанной (взята кровь или выдан результат) — для чека «полный расчёт». Продаём ли мы услугу лаборатории как агент (тогда нужны агентские признаки и данные поставщика: название и ИНН лаборатории).
4. **Цены:** ALEX2, взятие биоматериала, остаются ли «Консультация» и «Срочный результат» (их делает не лаборатория — кто оказывает?), промокоды и скидки (в макете «Скидка 99 % в лаборатории ALEX», «-100 % на консультацию» — это реальные акции?).
5. **Юридические тексты:** согласие на обработку ПДн и данных о здоровье, согласие на передачу лаборатории и ЮKassa, оферта (договор оказания услуг), правила отмены и возврата, обновление политики. Где их публикуем (на старте — `noindex`).
6. **Юрстатус:** есть ли у ИНМУНОТЕХ медицинская лицензия (лаборатория пишет «как от МО-юрлица»), уведомление РКН с категорией «здоровье», договор поручения обработки с лабораторией.
7. **Результаты:** храним ли PDF у себя и сколько, или только отдаём из ЛИС.
8. **Поддержка:** кто ведёт офисы в админке, обрабатывает отмены, возвраты, вопросы.

### 3.3 От лаборатории

Список из раздела 6.1 `alfalab-lis-plan.md` плюс:

- реальные JSON-примеры ответов и выгрузки справочников (см. раздел 0);
- код услуги взятия биоматериала для ALEX2 и перечень биоматериалов с услугами взятия;
- как считаются взаиморасчёты при оплате у нас (акт за месяц по `TotalPrice`?), что с оплаченным, но не сданным заказом;
- формат списка офисов (желательно таблица) и коды офисов.

### 4.1 Корзина — доработка макета

- **Блоки:** «Комплектация» (ALEX2 с ценой; строка «Взятие крови» с ценой, неотключаемая; «+IgE» как метка), «Также рекомендуем» (доп. услуги, если остаются), «Место сдачи анализа» (карточка выбранного офиса с адресом, часами и кнопкой «Изменить» или кнопка «Выбрать офис»), «Личные данные», правая колонка «Итого» (офис, время на результат, состав с ценами, промокод, сумма).
- **Поля:** Фамилия*, Имя*, Отчество (чекбокс «нет отчества»), Пол* (переключатель М/Ж), Дата рождения* (маска ДД.ММ.ГГГГ), Телефон* (+7, маска), E-mail* (нужен для чека и входа).
- **Согласия (3 чекбокса):** обработка ПДн и данных о здоровье; передача данных лаборатории; оферта и правила возврата. Ссылки на тексты. Кнопка активна, только когда отмечены все.
- **Кнопка:** «Перейти к оплате» с итоговой суммой.
- **Состояния:** офис не выбран (кнопка неактивна, подсказка); ошибка поля (красная подпись под полем: «Укажите фамилию», «Проверьте дату рождения», «Нужен e-mail — на него придёт чек»); возраст (если лаборатория берёт с ограничениями — текст-предупреждение); промокод применён / неверный / истёк; ALEX2 временно недоступен (приостановка в ЛИС) — плашка вместо кнопки оплаты; загрузка после нажатия (кнопка со спиннером); ошибка сервера («Не удалось оформить заказ, попробуйте ещё раз»).
- **Мобилка:** один столбец, итог и кнопка оплаты прилипают к низу экрана; блок «Итого» сворачивается.

### 4.2 Выбор офиса — доработка макета

- **Шаг 1, город:** выпадающий список городов из БД с количеством офисов; поиск при длинном списке.
- **Шаг 2, список офисов:** карточки (название сети/офиса, адрес, метро, часы будни/выходные, бейдж акции), поиск по адресу или метро, сортировка по алфавиту. Выбранная карточка раскрывается: адрес, часы, телефон, «Как подготовиться» (ссылка), кнопка «Выбрать».
- **Карта:** текущий макет — статичная подложка. Для реального списка нужна интерактивная карта (Яндекс Карты JS API: внешний скрипт и ключ) или список без карты со ссылкой «Открыть в Яндекс Картах». Предлагаю на старте список + ссылка; карту — отдельным решением.
- **Состояния:** в городе нет офисов; ничего не найдено по поиску; офис временно не принимает (серый, без кнопки); загрузка.
- **Мобилка:** как в макете — полноэкранный шаг, переключатель «Список / Карта», выбранный офис в нижнем листе с кнопкой «Выбрать».

### 4.3 «Спасибо» и статус оплаты — новый макет (`/cart/order/{uuid}`)

- **Состояния:**
  1. «Проверяем оплату» — спиннер, текст «Это займёт несколько секунд», автообновление.
  2. «Оплата прошла» — заголовок «Заказ оформлен», номер заказа; карточка офиса (адрес, часы, ссылка на карту); «Что дальше»: 3 шага (придите в офис с паспортом → назовите номер направления → результат придёт в кабинет примерно через N дней); номер направления крупно (когда пришёл из ЛИС; до этого — «Номер направления придёт на почту в течение часа»); кнопки «В личный кабинет» и «Скачать направление (PDF)».
  3. «Оплата не прошла / отменена» — причина простыми словами, кнопки «Попробовать ещё раз» и «Вернуться в корзину».
  4. «Заказ не найден» — ссылка на главную.
- **Блок:** «Чек отправлен на e-mail …».
- **Мобилка:** один столбец, кнопки во всю ширину.

### 4.4 Вход и восстановление — доработка (если вход по коду)

- Экран 1: «Добро пожаловать!», поле e-mail, кнопка «Получить код».
- Экран 2: «Введите код из письма», 6 ячеек, таймер «Отправить ещё раз через 0:59», ссылка «Изменить e-mail».
- Ошибки: «Почта не найдена — проверьте адрес из заказа», «Неверный код», «Код устарел», «Слишком много попыток, попробуйте через 10 минут».
- Если остаёмся на пароле: текущие макеты «Восстановление доступа» и «Проверьте почту» подходят, добавить экран «Задайте новый пароль».

### 4.5 Кабинет — доработка макета

- **Список заказов** (новое, если заказов больше одного): карточки с датой, номером, офисом, статус-бейджем, суммой. Один заказ — сразу открывается карточка.
- **Карточка заказа:** шкала из шагов «Оплачен → Ждём вас в офисе → Материал получен → Исследование → Результат готов» (ваши 4 статуса + «оплачен»); номер направления и кнопка «Направление (PDF)»; адрес офиса; «Сдайте кровь до …» (срок жизни направления); плановая дата готовности; кнопки «Скачать результат (PDF)» и «Отменить заказ» (только до сдачи крови, с подтверждением «Деньги вернутся на карту в течение … дней»).
- **Дополнительные состояния:** «Оформляем заказ» (оплачен, направление ещё не создано); «Нужна повторная сдача» (брак, текст лаборатории, контакт поддержки); «Заказ отменён, возврат оформлен / выполнен»; «Ошибка, мы уже разбираемся» (needs_attention глазами пациента); «Результат готов» + «Посмотреть онлайн» — убрать, если не делаем таблицу результатов (в MVP только PDF).
- **Мобилка:** как в существующих мобильных макетах ЛК.

### 4.6 Админка (без Figma)

«Офисы» (список, форма, импорт CSV), «Заказы ЛИС» (список с фильтрами по статусу, карточка с хронологией, кнопки «Повторить отправку», «Отменить и вернуть деньги»), «Платежи» (в карточке заказа), «Справочники ЛИС» (версия, ALEX2 доступен или приостановлен, кнопка «Обновить»). В стиле текущих разделов.
